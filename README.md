# 대구시 응급 골든타임 최적화 (경북대 ITS)

**2026 데이터+AI 혁신챌린지 · 데이터안심구역 경진대회**

---

## 한 줄 요약

> **지금 날짜·시각을 기준으로 “앞으로 교통이 얼마나 막힐지”를 예측하고,  
> 그 예측으로 소방·구급 출동 경로를 최적화해 골든타임을 줄인다.**

> **경로·혼잡 의사결정의 본체 = 표준노드링크 DiGraph (혼잡가중 최단경로 / 이후 RL 정책).**  
> 배차·ETA·이동이 이 그래프(또는 학습 정책) 위에 있다.

> **언제 온라인이고 언제 오프라인인가**  
> - **안심구역 = 학습·ITS 가공만** (인터넷 차단) → `ROUTING_ENGINE=graph`, 공개 OSRM·카카오 경로 API **호출 없음**  
> - **밖(온라인) = 관제 시연·결과 보기** → 지도 타일·(선택) OSRM/교통 API로 화면을 풍부하게 해도 됨

### 경로 엔진 한 줄 정리 (발표용)

| 단계 | 네트워크 | 경로 엔진 | 말하는 법 |
|---|---|---|---|
| **학습 (안심구역)** | 오프라인 | **DiGraph** (+ RL) | 혼잡이 엣지 비용·정책에 들어가 **길을 고른다** |
| **시연·관제 (온라인)** | 인터넷 OK | graph 기본, 원하면 `osrm` | OSRM은 **도로 곡선·주행 기하** 보강. 혼잡 예측·배차 논리는 여전히 우리 쪽 |

> 한 문장: **학습은 안심구역에서 오프라인으로 돌리고, 나중에 온라인에서 관제 화면으로 본다. 안심구역 안에서는 공개 OSRM을 경로 본체로 쓰지 않는다.**

지금은 **보여주기(관제 데모)** 단계이고, 이후 안심구역 ITS + RL 학습으로 같은 자리를 학습 모델이 대체한다.

## 1. 핵심 아이디어

### 1-1. 무엇을 최적화하나

대구 시내 **119 출동**에서 막히는 길을 피해 도착 시간을 줄이는 것.

| 상황 | 출동 | 종료 |
|---|---|---|
| **화재** | 소방서 → 화재현장 | 현장 도착 |
| **교통사고·인명피해** | 소방서 → 사고현장 → **응급실** | 응급실 도착 |
| **복합(예: 차량화재)** | 소방차 + 구급차 **동시** | 각자 임무 종료 |
| **대형·다수 사상** | 여러 대 동시 출동 | 자원·경로 전역 배정 |

중요: “1단계/2단계”는 **한 임무의 순차 진행 이름**이 아니라,  
**사고 유형이 다르면 아예 다른 시나리오**라는 뜻이다.

### 1-2. 중앙관제 관점

사용자는 **중앙관제센터** 역할이다.

1. 지도에서 **사고 좌표를 직접 찍는다** (여러 곳 가능)
2. 사고마다 **화재 / 인명피해 / 복합**과 규모를 고른다
3. 시스템이 전역으로 결정한다  
   - 어느 **소방서**에서 나갈지  
   - (구급) 어느 **응급실**로 갈지  
   - 여러 대가 움직일 때 **경로가 서로 안 겹치게**  
4. 차량은 GPS처럼 **도로 구간 이동시간**만큼 실제로 움직인다  
5. **소방서별 구급·소방 잔여 대수**를 보고, 잔여가 있는 **가장 가까운(경로비용 최소) 서**에서 출동한다. 출발하면 잔여 −1, 임무 끝나면 +1  
6. 시간이 흐르며 혼잡이 바뀌면 **남은 길을 다시 잡는다(재경로)**

> 119 구급의 출발지는 **소방서(안전센터)** 이다. 병원은 **이송 목적지**이며, 병원 소속 민간구급과는 별개다.

### 1-3. 교통은 2차원이 아니라 시간축이 있다

도로 혼잡은 `(위치, 시각)` — 더 정확히는 **날짜 유형까지** 본다.

- 평일 출퇴근 피크
- 주말 오후 나들이
- **추석·설 연휴** 귀성·귀경
- 지금 시각 기준 **앞으로 몇 시간** 동안 얼마나 빡셀지 **예측**

그 예측 costmap으로 경로 비용을 매겨, “지금 비어 보여도 곧 막힐 길”을 미리 피한다.

지도에서는 교통량을 **파랑(한산) → 빨강(혼잡)** 으로 한눈에 본다.

### 1-4. 왜 만드나 (기존 내비와의 차이)

일반 내비·지도 앱도 “지금 어디가 막히는지”는 보여 준다.  
다만 보통은 **현재(또는 아주 가까운 과거) 실시간 혼잡**을 보여주는 쪽에 가깝고,

- **앞으로 1~몇 시간** 교통량이 어떻게 바뀔지,
- 평일/주말/**추석·설**처럼 날짜 유형이 바뀌면 패턴이 어떻게 다른지,
- 그걸 반영해 **지금 출발하는 응급차의 최적 경로**를 다시 짜는지

까지를 한 파이프로 다루는 경우는 드물다.

이 프로젝트의 목적은 그 빈틈을 채우는 것이다.

1. **과거** 오픈 링크 시간통계(+선택 ITS 15분) + **현재** 시각·날짜 맥락  
2. → **미래 혼잡 예측** (costmap의 시간축)  
3. → 그 예측으로 **출동 최적 경로** (소방/구급, 다중 사고·다중 차량)  
4. → 관제 화면에서 **실시간처럼** 경로·이동·재탐색을 확인

즉 “실시간 교통 표시”를 넘어서, **예측 → 경로 최적화 → 골든타임 단축**까지가 목표다.

### 1-5. 지금 vs 나중

| 단계 | 역할 |
|---|---|
| **지금 (표현/데모)** | 웹 관제 + **오픈데이터** 시간대 속도 예측 + 혼잡가중 경로 |
| **나중 (학습)** | 오픈 통계(+선택 ITS)로 혼잡·경로 정책을 학습 (PPO) |

데모와 학습은 **같은 문제 정의**를 공유한다. 데모의 예측·경로 자리를 나중에 학습 모델이 채운다.

|---|---|---|---|
| **1** | 예측 MAE/RMSE | 오픈 holdout 수치 나옴 | 같은 구간·시간으로 ITS와 나란히 → **왜 안심구역인지** 숫자 |
| **2** | PPO vs Dijkstra | `train.py` 후 비교 | 동일 (학습은 안심구역에서) |

## 3. 시스템 구조 (아이디어 → 코드)

```
[사용자 = 중앙관제]
  사고 좌표·유형 (시각 = 화면의 “지금”)
        │
        ▼
 congestion_time.py
  · 평일/주말/추석·설 캘린더
  · linkspeed + 시간통계 → 경로용 향후 혼잡 예측
  · 지도용 파랑→빨강 costmap (우선순위 샘플)
        │
        ▼
 dispatch_center.py / dispatch_web.py
  · 소방서·응급실·경로 전역 배정
  · 경로 겹침 페널티 (Prioritized Planning)
  · 차량 실이동 + 재경로
        │
        ▼
 (나중) train.py + EmergencyRouteEnv
  · ITS 실제 교통량으로 같은 문제를 RL 학습
```

지도 뼈대는 **대구 표준노드링크** (`data/standard_node_link/`).  
클릭 위치는 배경 OSM과 100% 일치하지 않을 수 있고, **우리 도로 그래프의 최근접 노드로 스냅**된다.

### 4-3. 지도 교통색(costmap) — 데이터 흐름과 “끊김”

**한 줄:** `linkspeed`(지금) + `link_hourly_stats`(패턴) + 캘린더 → **경로 비용·지도 색**. 배경 지도(OSM/카카오·네이버 타일)와 **링크별 교통 원천은 다르다**. 공개 범위에서 링크 단위·미래 패턴까지 쓰려면 **공공데이터가 본체**다.

```
표준노드링크 그래프
    ├─ linkspeed API ──► 링크/도로명 매칭 → 지금 혼잡 (전 링크 X, 대구 약 수천 링크 중 일부)
    ├─ link_hourly_stats → build_open_speed_profile.py → 시간대 속도 → 예측 cost
    └─ congestion_time.costmap → Leaflet polyline (파랑→빨강)
```

| 끊겨 보이는 이유 | 설명 |
|---|---|
| **1. API·통계 커버리지** | 실시간 API는 **전 구간을 주지 않음**. 통계 CSV도 샘플이면 도로명 매칭 구멍이 생김. |
| **2. 표준노드링크 ≠ OSM** | 노드는 **교차점** 위주라 구간이 짧거나 길게 끊겨 보일 수 있음. 긴 직선은 **맵을 가로지르는** 고속 등이라 **의도적으로 숨김**. |
| **3. 표시 한도** | costmap은 성능상 **우선순위 샘플**(실시간·통계 맞은 도로·짧은 구간 우선, 최대 ~3800 segments). |

**경로·차량 이동 (기본 `graph`):** 탐색·배차·ETA·폴리라인·이동이 모두 표준노드링크 **DiGraph 혼잡가중 최단경로**다. 차량은 `edge_segments`(링크 1개 = `edge_times` 1칸)를 따른다. 구간 양끝은 **그래프 노드(또는 클릭 현장) 좌표**에 맞춘다.

**OSRM (`ROUTING_ENGINE=osrm`) — 온라인 시연 보강용:**  
안심구역 **학습** 단계에서는 쓰지 않는다. 밖에 나와 관제 데모할 때 도로 곡선을 살리고 싶으면 공개 OSRM 또는 로컬 backend:

```bash
ROUTING_ENGINE=osrm
OSRM_URL=https://router.project-osrm.org/route/v1/driving   # 온라인 시연
# OSRM_URL=http://127.0.0.1:5000/route/v1/driving         # 로컬 backend
```

혼잡 예측·배차 논리의 본체는 여전히 표준노드링크(+학습 정책)이다.
**완화 방법 (로컬에서 할 수 있는 것)**

## 5. 모델·차원·보상·손실 (학습 설계)

정답 경로 CSV가 없으므로 **자기지도 강화학습**이다.  
시뮬레이터(`EmergencyRouteEnv`)가 매 스텝 보상으로 “잘한 길/못한 길”을 알려 주고, 정책이 그걸 최대화하도록 학습한다.

### 5-1. 왜 PPO인가

| 항목 | 선택 | 이유 |
|---|---|---|
| 알고리즘 | **PPO** (Stable-Baselines3) | 행동이 **이산**(이웃 교차로 K개 중 하나 선택). 교차로 그래프 위에서 “다음 링크”를 고르는 MDP에 맞음 |
| 정책 타입 | `MlpPolicy` + 커스텀 feature extractor | 관측이 **고정 길이 벡터**(이미지/시퀀스 아님) → MLP가 단순·안정 |
| (나중) 로보레이서 | PPO → **SAC** 등으로 교체 | 조향·가속은 **연속 행동**. body(특징추출기)는 재사용하고 head·알고리즘만 교체 |

손실(학습 목표)은 SB3 PPO 기본식이다.

- **정책 손실 (Clipped Surrogate)**: \(L^{CLIP}(\theta)\) — 이전 정책 대비 비율을 클립해 과도한 업데이트를 막음  
- **가치 손실**: \(\bigl(V_\theta(s) - R_t\bigr)^2\) — 누적 보상(리턴) 추정  
- **엔트로피 보너스**: 탐험 유지  
- 전체: \(L = L^{CLIP} - c_v L^{VF} + c_e S[\pi]\) (부호·계수는 SB3 구현 따름)

하이퍼(코드 기준): `n_steps=256`, `batch_size=256`, `gamma=0.99`, `lr=3e-4`, `n_envs=4`.

### 5-2. 관측 벡터 몇 차원인가 (24차원)

교차로마다 나갈 수 있는 길이 최대 **K=5**개라고 두고, 그 이웃만 본다.

| 구간 | 차원 | 내용 |
|---|---:|---|
| 이웃 링크 특징 | **15** | 이웃 \(i=0..4\)마다 `[travel_time/10, risk, congestion]` → \(5 \times 3\) |
| 이웃 유효 마스크 | **5** | 실제로 존재하는 이웃=1, 패딩=0 (가짜 행동을 막기 위함) |
| 목표까지 hops | **1** | 남은 홉 수 / MAX_STEPS (정규화) |
| 누적 위험 | **1** | 지금까지 지나온 risk 합 (상한 클리핑 후 정규화) |
| 차종 원핫 | **2** | `[ambulance, fire_truck]` — 임무 구조가 다르므로 상태에 명시 |
| **합계** | **24** | `EmergencyRouteEnv` observation |

부모 `HighwayRouteEnv`만 쓰면 차종 없이 **22차원**. 응급 env에서 +2.

**행동 공간:** `Discrete(5)` — 유효 마스크 밖의 인덱스를 고르면 즉시 큰 페널티 후 에피소드 종료(불법 행동).

**에피소드 길이:** 응급 env `MAX_STEPS=80` (시내 경로가 고속도로보다 김).

### 5-3. 네트워크 레이어는 어떻게 / 왜 이렇게 짰나

`policy.py`의 `SharedBodyExtractor` (특징추출 body):

```
입력 24차원
  → Linear(24 → 128) + ReLU
  → Linear(128 → 128) + ReLU
  → Linear(128 → 64)  + ReLU     ← features_dim=64
  → (SB3가 붙이는) Actor head  →  각 행동 로짓 (5)
  → (SB3가 붙이는) Critic head →  상태가치 스칼라 V(s)
```

| 설계 | 이유 |
|---|---|
| **입력층만 관측 차원에 종속** | 안심구역(24) → 로보레이서(LiDAR 등)로 옮길 때 body 구조는 그대로 두고 입력 차원만 바꿈 |
| **hidden 128 × 2** | 표 형태 관측에 충분한 용량. 너무 크면 과적합·전이 어려움 |
| **features_dim=64** | actor/critic이 공유하는 압축 표현. 정책·가치 head가 같은 “상황 요약”을 보게 함 |
| **ReLU MLP** | 비선형 경계(막힌 길 vs 뚫린 길)를 표현하면서도 학습이 단순 |
| **공유 body + 분리 head** | 같은 도로 감각을 배우되, “어느 링크로 갈지”(actor)와 “이 상황이 얼마나 좋은지”(critic)는 역할이 다름 |

즉 레이어를 깊게 CNN/Transformer로 안 짠 이유는, 입력이 **로컬 이웃 K개의 표 특징**이라 공간 격자·장거리 어텐션이 필수는 아니기 때문이다. (전역 배정·다중 차량은 관제 쪽 Prioritized Planning이 담당.)

### 5-4. 보상 함수 (매 스텝)

시내 응급은 **시간·혼잡이 골든타임의 핵심**이라, 고속도로용보다 위험 가중을 낮추고 혼잡 항을 넣었다 (`RISK_LAMBDA=1.0`, 혼잡 계수 `0.8`).

한 스텝에서 이웃 링크를 골랐을 때:

\[
r \;=\; r_{\mathrm{step}}
 \;-\; \underbrace{t/10}_{\text{이동시간}}
 \;-\; \lambda\, \mathrm{risk}
 \;-\; 0.8\,\mathrm{congestion}
 \;+\; r_{\mathrm{event}}
\]

| 항 | 값 (코드) | 의미 |
|---|---|---|
| \(r_{\mathrm{step}}\) | `-0.05` | 괜히 빙빙 돌지 말 것 |
| 이동시간 | `-travel_time/10` | 빠른 길 선호 |
| 위험 | `-\lambda·risk`, \(\lambda=1.0\) | 위험 구간 회피 (시내는 보조) |
| 혼잡 | `-0.8·congestion` | 막힌 길 회피 (골든타임) |
| 불법 행동 | `-5.0` | 없는 이웃 선택 시 + 종료 |
| 현장 도착 (구급 출동→이송 전환) | `+5.0` (`PHASE_BONUS`) | 1차 목표 달성 |
| 최종 도착 (응급실 / 화재현장) | `+10.0` (`GOAL_BONUS`) | 임무 완료 |

- **구급:** 소방서→현장(`dispatch`) → 현장→응급실(`transport`). 현장 도착 시 phase 전환 보상.  
- **소방:** 소방서→화재현장만. 현장 도착이 곧 종료 보상.  
- 이송 중 병원 변경: `reroute()` (구급 전용). 스텝 한도만 조금 늘리고 재학습 없이 같은 정책 사용.

데모 단계(학습 전)에는 같은 비용을 **혼잡가중 다익스트라**로 풀어 경로를 보여 준다. RL은 그 “비용 감각”을 정책으로 체화하는 단계다.

### 5-5. 데이터 → 학습 흐름

```
표준노드링크 뼈대 + 오픈 링크속도 혼잡(시·요일·연휴 보정)
        │
        ▼
 EmergencyRouteEnv  (관측 24차원 / 행동 Discrete(5))
        │
        ▼
 SharedBody 24→128→128→64  +  PPO Actor/Critic
        │
        ▼
 웹 관제의 “예측 반영 경로” 자리를 학습 정책으로 교체
```

- 토폴로지(불변) / 혼잡(가변)  
- 에피소드마다 차종·목표·시간대를 바꿔 **goal-conditioned** 일반화  
- `python train.py --timesteps 300000` (기본: 소방+구급 혼합)

## 7. 한계 (발표용 정직 문구)

- ITS에 **사고 발생 좌표 테이블 없음** → 현장은 교차로/노드 스냅 근사  
- **응급실 병상 실시간 없음** → 병원은 비용·부하 분산으로 선정, AI는 경로 중심  
- 표준노드링크가 OSM 전 골목과 1:1은 아님 → 시설·그래프 경로는 최근접 노드 기준. **I마커·현장 = 클릭 좌표** (스냅으로 옮기지 않음)  
- 소방서·병원 아이콘은 **실제 좌표**, 출동 경로는 **스냅 노드**에서 시작/종료  
- 지도 교통색은 **전 도로 연속**이 아니라 API·통계·표시 한도의 **우선 샘플** (자세히 **§4-3**)  
- 링크 시간통계 샘플은 포털 원본으로 교체 권장. 실시간 API·전국 병상 API는 키 발급 후 연결  
- 안심구역 PC는 오프라인 → 카카오내비 대신 **자체 관제 지도/전광 연동** 제안
